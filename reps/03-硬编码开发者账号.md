# PROBLEM TYPE

## Vulnerability Type

- Use of Hard-coded Credentials — CWE-798

## Root Cause

```php
// initialize.php:2
$dev_data = array('id'=>'-1','firstname'=>'Developer','lastname'=>'',
    'username'=>'dev_oretnom',
    'password'=>'5da283a2d990e8d8512cf967df5bc0d0', ...);
```

The bootstrap hard-codes a developer account (`dev_oretnom` with an unsalted MD5 password hash) shipped in every download of the product. The same artifact appears across the vendor's PHP/OOP template family, so every deployment carries an identical, publicly documented credential pair.

## Impact

Anyone who reads the public source knows a valid credential hash for all deployments of this product family. Where the login flow consults the developer record (fallback/maintenance paths common in this template family) this yields direct unauthorized access; at minimum it documents the account naming and hash scheme, and the unsalted MD5 enables offline recovery of the shared password once any instance's database is exfiltrated (see report 01, unauthenticated SQL injection).

# No login or authorization is required to obtain the credential material (it is in the public download)

# Vulnerability details and POC

- Static evidence: `initialize.php:2` as quoted above (file in the public download, workspace copy `workspace/sc15184/reps/initialize.php`).
- Hash format: 32-hex unsalted MD5, matching the `users` table password scheme used by the login flow.

# Suggested repair

1. Remove the hard-coded developer record from shipped source entirely; provision admin accounts at install time with per-installation random credentials.
2. Store password hashes with `password_hash()` (bcrypt/argon2), never MD5.
3. Add an audit for known credential artifacts before release.
